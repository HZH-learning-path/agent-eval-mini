## 四、归因结论

1. **整体结论**
   - 基线（A组）通过率：100%
   - 仅限制token（B组）通过率：25%，下降 75 个百分点
   - 仅改变工作目录（C组）通过率：50%，下降 50 个百分点
   - 仅改变执行层的一个配置，通过率即可显著下降，验证了'Agent分数混叠'问题

2. **B组（token限制）失败归因**
   - 共 3 道题失败
   - 其中 2 道题是工具调用JSON参数被截断（Unterminated string / JSON解析错误）
     → 模型知道该调什么工具、传什么参数，但输出空间不够，参数写了一半被截断
     → 工具根本没被执行，任务直接失败。这是执行层配置问题，不是模型推理能力问题
   - 其中 1 道题是模型直接回答时输出被截断
     → 模型选择了不调工具直接回答，但回答没说完就被截断了
   - 值得注意：B组通过的题目中，部分是模型'猜对'的（无需调用工具或直接给出答案），并非真正完成了工具调用

3. **C组（错误路径）失败归因**
   - 共 2 道题失败
   - 其中 1 道题是文件不存在导致的执行失败
     → 模型正确调用了工具（read_file/extract_zip），参数也正确
     → 但工作目录指向不存在的路径，文件找不到
     → 模型的行为完全正确，是执行层环境配置错误
   - C组通过的题目（task2, task4）包括：
     → 纯推理题（无需文件操作）：路径错误不影响
     → 写入类任务：write_file 会自动创建目录，所以不受路径不存在的影响
     → 这说明不同类型的任务对执行层配置的敏感度不同，评测需分类分析

4. **核心发现**
   - 同一个模型、同一套题、同一个评分标准，仅改执行层配置，通过率可差 75 个百分点
   - 分数低 ≠ 模型能力差，可能是执行层配置的问题
   - Agent 评测必须拆分模型层和执行层，否则分数没有意义
   - 不同任务类型对执行层配置的敏感度不同，需要分类归因

## 五、实验局限与后续方向

- 任务数量较少（4题），统计意义有限，后续可扩充至20-30题
- 仅测试了两个执行层维度（token限制/路径错误），真实Agent框架涉及更多维度（沙箱、权限、压缩等）
- 单模型测试，未做跨模型验证；后续可加入更多模型对比
- 任务以文件操作为主，未能覆盖Agent的更多能力维度
- 未来方向：接入真实Agent框架（如DeepSeek Harness），在更复杂的环境中验证归因方法
